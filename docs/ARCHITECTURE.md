# svsCloud — архитектура

Утилита для монтажёров: открыть папку на Яндекс.Диске или Google Диске
(свою или по чужой ссылке), посмотреть превью, отметить нужное и скачать
с докачкой. Собрана в один `.exe` для Windows.

---

## 1. Выбор стека

| Вариант | Почему не взяли | Почему взяли Python + PySide6 |
|---|---|---|
| **Electron + Node.js** | На машинах команды Node не установлен, нужна сборка фронта, два процесса (main/renderer) и IPC — лишняя сложность ради UI, который всё равно пришлось бы писать на HTML | — |
| **C# / WPF** | Отличный вариант для Windows-десктопа, но в команде нет .NET-разработчика; питон есть везде | — |
| **Python + Tkinter** | Нет нормального видеоплеера с перемоткой, виджеты выглядят «из 2005 года» | — |
| **Python + PySide6/Qt** | ✅ | Единый язык с бэкендом и API, Qt даёт нативные виджеты **и** QWebEngineView (Chromium) — встроенный плеер с Range-запросами и перемоткой; PyInstaller собирает один `.exe`; ffmpeg/ffprobe подключаются как внешний процесс |

**Итог:** Python 3.12+ / PySide6 6.12 (Essential + WebEngine) / httpx (async) /
SQLite (кэш) / PyInstaller (сборка). Зависимостей ровно четыре.

Почему **asyncio + httpx**, а не `requests` в потоках: сетевых потоков
одновременно десятки (файлы × сегменты), асинхронный I/O масштабируется
линейно по памяти, а `asyncio.Semaphore` даёт один понятный регулятор
нагрузки на API. GUI остаётся синхронным — общение через сигналы Qt.

## 3. Ключевые алгоритмы

### 3.1 OAuth

* **Яндекс** — консольное приложение, авторизация по коду подтверждения.
  Redirect URI — `https://oauth.yandex.com/verification_code`: Яндекс
  показывает на этой странице **код из 7 цифр** (живёт 10 минут), программа
  подставляет его из буфера обмена. Параметр `scope` намеренно **не
  передаём** — тогда токен выдаётся с теми правами, которые заданы при
  регистрации приложения (иначе ловим `invalid_scope`).
  Токены обновляются через `grant_type=refresh_token`.
* **Google** — тип «Desktop app»: приложение поднимает `127.0.0.1:<случайный порт>`,
  открывает системный браузер, Google возвращает код на `http://127.0.0.1:PORT/`.
  Пользователю ничего делать не нужно.
* Токены живут в `%APPDATA%\svsCloud\tokens.dat`, зашифрованы DPAPI.
* `OAuthManager.access_token()` сам обновляет токен за 2 минуты до истечения;
  при неудаче refresh — просит войти заново.
* Для Яндекса передаётся `device_id` — в настройках Яндекс ID видно,
  какое устройство имеет доступ к диску, и его можно отозвать.

### 3.2 Получение дерева файлов

* Яндекс: `GET /v1/disk/resources?path=…&limit=1000&offset=…`
  (для публичных — `/public/resources` с `public_key`). Постранично, `offset`
  наращивается, пока не выбрана вся выборка; страницы ограничены 1000 записей.
* Google: `GET /drive/v3/files?q='<id>' in parents and trashed=false`
  с `pageToken`, `supportsAllDrives=true`, `includeItemsFromAllDrives=true`.
* Интерфейс грузит папки **лениво**: раскрыли папку → запрос → подстановка.
  При «Моём диске» на каждый файл приходится отдельный запрос — поэтому
  список папок кэшируется в SQLite (`metadata_cache`).

### 3.3 Очередь загрузок

```
engine.enqueue(files)
   └── asyncio.Queue ──► N воркеров (max_parallel_files)
                            └── Transfer.run(job)
                                  ├── resolve_download()  → href / alt=media
                                  ├── план сегментов (64 МБ по умолчанию)
                                  ├── по segment-задаче: GET с Range: bytes=…
                                  └── склейка + проверка MD5 + переименование
```

* **Параллелизм двухуровневый:** 4 файла × 4 сегмента = до 16 одновременных
  HTTP-потоков, общий семафор ограничивает общий объём.
* **Докачка:** каждый сегмент помнит, сколько байт уже принято, и продолжает
  с `Range: bytes=start+received-end`. Состояние пишется в `<имя>.part.json`.
* **Восстановление:** при старте программа сканирует папку загрузок на
  `*.part.json` и продолжает с места обрыва.
* **Протухшая ссылка:** Яндекс отдаёт `href` на ~30 минут. При 403/404
  ссылка перевыпускается, а сегмент продолжается с прежнего места.
* **Сервер не умеет Range:** если пришёл 200 вместо 206 — файл перекачивается
  одним потоком с начала, дальше докачка идёт по смещению.

### 3.4 Превью

1. Локальный сервер на `127.0.0.1:<порт>` отдаёт `/player/<token>` —
   страницу с `<video controls src="/media/<token>">`.
2. `/media/<token>` тянет облако и **проксирует Range** — Chromium шлёт
   `Range: bytes=…` при перемотке, значит файл не качается целиком,
   а монтажёр видит кадры с нужного места.
3. Форматы, которые не играет браузер (mkv, avi, prores), ffmpeg
   перекодирует в короткий mp4 (первые 60 секунд, 480p) — в фоне,
   с индикатором в статусе.
4. Постер: Яндекс отдаёт готовый `preview` в метаданных, Google — `thumbnailLink`.

## 5. Подводные камни API

### Яндекс.Диск

Формат ответов API менялся; сверено с
[документацией](https://yandex.ru/dev/disk-api/doc/en/reference/public.md),
эталонной библиотекой [yadisk](https://github.com/ivknv/yadisk)
**и живыми запросами к настоящему API**.

| Проблема | Что происходит | Решение в проекте |
|---|---|---|
| **Дети лежат в `_embedded.items`**, а не в корне ответа | Читаем `items` → получаем пустой список, дерево пустое | `unpack_listing()` берёт `_embedded`, при отсутствии — корневой `items` (старый формат) |
| **Тип папки — `"dir"`, а не `"folder"`** | Папка превращается в файл | Принимаем оба значения |
| **`public_key` — не то, что стоит в ссылке** | Короткий идентификатор из `/d/XXXX` API не понимает → 404 | Передаём **полную ссылку** `https://disk.yandex.ru/d/XXXX` — API принимает именно её (проверено: короткий ключ всегда даёт 404, полный URL работает) |
| **Ссылка открывается в браузере, но не в API** | Владелец закрыл «Доступ по ссылке»: браузер показывает папку авторизованному пользователю, а публичный API отвечает 404 | Понятное сообщение: «Яндекс не даёт доступ по этой ссылке без входа. Если папка открыта вам лично — войдите и откройте через “Мой диск”» |
| **Путь своего диска требует схемы** | `path=/Папка` работает не всегда | Отправляем `path=disk:/Папка` |
| **Докачку обрывает сервер** (архивы, `media_type=compressed`) | Яндекс отдаёт первые ~460 КБ файла, дальше рвёт соединение; обычный GET без Range зависает | Дважды обрыв → переход на один поток без Range с коротким таймаутом; если и так не выходит — понятная ошибка, а не зависание. **Видео и аудио (`media_type=video`) не affected** — проверено на файле 505 МБ |
| **Без `Range` сервер не отдаёт файл** | GET без диапазона висит или обрывается | Всегда работаем через диапазоны; одиночный поток тоже шлёт `Range: bytes=N-` |
| **Код подтверждения — 7 цифр, живёт 10 минут** | Вставили ссылку или старый токен | Проверка формата + понятное сообщение; код подставляется из буфера |
| **Redirect URI — `oauth.yandex.com/verification_code`** | Старый `oauth.yandex.ru/redirect` больше не подходит | Основной + запасные варианты, перебор при обмене кода |
| **Scope'ы поменялись**: `cloud_api:disk.read` вместо `login:info` | `invalid_scope` | `scope` не передаём — права берутся из регистрации приложения |
| **Ошибки в формате `{"error": ..., "error_description": ...}`** | Парсер не узнаёт код | Разбор обоих форматов + таблица человеческих формулировок |
| `href` на скачивание живёт ~30 минут | Через полчаса активной загрузки — 403 | Ссылка перевыпускается; сегмент продолжается с прежнего смещения |
| Постраничный листинг | `limit` максимум 1000, `total` обязателен | Цикл с `offset` до конца выборки, защита от бесконечного цикла (50 страниц) |
| Публичные ссылки ограничены по трафику | 429/503, «not enough bandwidth» | Token bucket + заморозка на `Retry-After` + понятное сообщение «Яндекс ограничил полосу для этой ссылки» |
| Публичная ссылка на файл, а не на папку | В `_embedded` пусто, ответ — сам файл | Показываем файл как единственный элемент списка |
| Нет `Range` на некоторых `href` | Сервер отвечает 200 целиком | Откат на один поток + докачка по смещению |
| Ошибки приходят текстом, а не JSON | Невозможно разобрать код | `friendly_error` смотрит и тело, и код ответа, и текст исключения |

### Google Диск

| Проблема | Что происходит | Решение в проекте |
|---|---|---|
| Квоты: 10 000 запросов / 100 с, 403 `rateLimitExceeded` | Массовые 403 при обходе дерева | Token bucket (4 req/s по умолчанию), backoff с джиттером, кэш метаданных в SQLite |
| Дневная квота на скачивание (5 ТБ на проект) | 403 `dailyLimitExceeded` | Отдельная человеческая формулировка + предложение продолжить позже |
| `files.list` не отдаёт файлы «вне папок» | Файлы без родителя не видны | Явно помечаем: в «Моём диске» видны объекты верхнего уровня |
| `alt=media` не работает для Google Документов | 403 «cannot be downloaded» | Отдельная ветка `files.export` (PDF/XLSX/PNG) |
| Экспорт Google Документов ограничен ~10 МБ | 403 на больших документах | Понятное сообщение; исходник при этом не скачается вовсе |
| Ярлыки (shortcuts) | `mimeType` = shortcut, а не файл | Разворачиваем в цель ярлыка (`shortcutDetails.targetId`) |
| Общие диски (shared drives) | Нужен `corpora=drive&driveId=…` | Список общих дисков читается через `drives.list`, `driveId` прокидывается в контекст |
| `resourceKey` для файлов по ссылке | Без него 404 | Ключ сохраняется в модели и передаётся в `files.get`/`alt=media` |
| Публичная папка без входа | `files.list` требует API-ключа | Ключ настраивается в «Настройках»; иначе просим войти в аккаунт |

### Общие

* **Скорость.** Прямые ссылки Яндекса отдаются с `downloader.disk.yandex.ru` и
  ограничены по полосе. Параллельные сегменты обходят это, но не нарушают
  лимиты: суммарный объём запросов ограничен семафорами.
* **Имена файлов.** В облаке встречаются символы, запрещённые в Windows
  (`:` `?` `*` …) — имена нормализуются при постановке в очередь.
* **Двоеточие в пути.** Структура папок облака воспроизводится внутри папки
  загрузок, поэтому файлы с одинаковым именем из разных папок не спорят.
* **Права.** Публичная ссылка Яндекса — это фактически анонимный доступ:
  в журналах не видно, кто скачивал. Если исходники   чувствительные —
  только свои аккаунты (`drive.readonly` для Google, `cloud_api:disk.read`
  для Яндекса).

## 6. Стратегия обхода лимитов

1. **Кэш метаданных** (SQLite): повторное открытие одной папки не тратит
   запросы; `file_id` и `md5` запоминаются.
2. **Кэш ссылок**: `href` Яндекса переиспользуется, пока не истёк (25 минут TTL).
3. **Token bucket**: 4 запроса/сек на провайдера, пауза при 429.
4. **Backoff**: 1.5с → 3с → 6с → … (потолок 90 с), джиттер ±35 %, `Retry-After`
   имеет приоритет.
5. **Ленивое дерево**: не обходим облако целиком, пока пользователь не раскрыл папку.
6. **Параллелизм на стороне скачивания**: много сегментов = выше скорость
   без дополнительных *запросов к API* (один `alt=media`/`href` на файл,
   дальше идут Range-запросы того же ресурса).

## 7. Проверка на живом API

Поведение Яндекса меняется без предупреждения, поэтому ключевые сценарии
проверены настоящими запросами к `cloud-api.yandex.net`:

| Проверка | Результат |
|---|---|
| Список публичной папки/файла | ✅ элементы приходят в `_embedded.items`, тип папки `dir` |
| `public_key` = полный URL vs короткий ключ | ✅ работает **только** полный URL; короткий — всегда 404 |
| Вложенная папка публичного ресурса | ✅ корень + подпапка + файлы по 10 ГБ |
| Скачивание файла 505 МБ (видео) | ✅ файл скачан целиком, **MD5 совпал** с MD5 из метаданных API |
| Докачка сегментами (`Range`) | ✅ работает, скорость ~7 МБ/с на один поток |
| Диапазонные запросы по архиву (`media_type=compressed`) | ⚠️ сервер отдаёт только первые ~460 КБ и рвёт соединение — сделали откат на один поток с коротким таймаутом |
| Ссылка, открытая авторизованным пользователем в браузере | ⚠️ публичный API отвечает 404 — доступ к таким папкам возможен только через «Мой диск» |
| Программа целиком: открытие живой публичной папки | ✅ дерево, размеры, даты, чекбоксы (скриншот ниже) |

> **Вывод про UI.** Дерево файлов впервые проверялось только запуском программы
> с настоящим облаком — и сразу вскрыло три ошибки в работе с
> `QStandardItemModel` (`rowCount`/`removeRows`/`appendRow` ждут индексы,
> а не `QStandardItem`; у `QStandardItem` нет `setExpanded`). Такие ошибки
> не ловятся ни тестами провайдера, ни моками API — поэтому добавлены
> headless-тесты интерфейса (`tests/test_ui_tree.py`) и запуск со ссылкой
> из командной строки: `svsCloud.exe --open https://disk.yandex.ru/d/KEY`.

---

## 8. Сборка и запуск

```powershell
python -m pip install -r requirements.txt
python run.py                       # разработка
python -m unittest discover -s tests -t .   # тесты
powershell packaging\build.ps1       # сборка dist\svsCloud.exe
```

Собранный `.exe` хранит настройки, токены и журналы в
`%APPDATA%\svsCloud\`. Ключи приложений вводятся монтажёром в
«Настройках» или поставляются централизованно через переменные окружения
`SVSCLOUD_YANDEX_CLIENT_ID` / `SVSCLOUD_GOOGLE_CLIENT_ID` и т. д.

## 9. Что осознанно не сделано (и почему)

* **Массовая авторизация через сервис-аккаунт** — потребовала бы отдельного
  веб-сервиса и хранения токенов команды на стороне вендора. Сейчас
  достаточно двух ключей, заданных в настройках.
* **Синхронизация превью в облаке** — предпросмотр монтажёрам нужен локально.
* **Планировщик по расписанию** — задача «сотни файлов» решается очередью
  и восстановлением после рестарта, но расписание лучше добавлять после
  стабилизации.
* **Автоподбор кодека в плеере** — Chromium в QtWebEngine не играет mkv;
  это закрыто через ffmpeg-прокси, а не сменой плеера.
* **Копирование публичного файла в свой диск** (`save-to-disk`) — спасло бы
  скачивание архивов, которые Яндекс.Диск отдаёт только «первым куском».
  Требует входа в аккаунт и оставляет копию в «Моём диске», поэтому пока
  не сделано: для видео (главный сценарий) проблемы нет.
